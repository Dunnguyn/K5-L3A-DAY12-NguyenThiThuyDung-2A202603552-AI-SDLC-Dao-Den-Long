# Four phase retrospective — Đảo Đèn Lồng

This project grew from a playable Night into a three island campaign with fuel and dawn survival, then gained performance runners, a local leaderboard and accessibility controls. Phase 4 is still preparation: the ten Night soak RSS requirement fails, so this document does not represent a v1.0.0 release.

**Phase 1.** A deterministic, DOM free Core and headless adapter established an executable baseline. The shared Core let later browser features and CLI scenarios exercise the same rules. Its contract source was only an internal draft; the official v1.0 schema was never supplied. We should have resolved that gap earlier because each later contract delta inherits it.

**Phase 2.** Three maps, enemies, wind, pads and the campaign made the game substantially harder to verify. Independent QA found seven concrete defects, including dash direction/speed, residual velocity, terrain penetration, stale dash visuals, Drifter overlap, event validation and lantern color. Targeted tests and browser evidence caught issues that the original passing unit suite missed. Codex repaired them, but the owner explicitly waived an additional independent QA re-test. The record correctly distinguishes a Codex rerun of 42 assertions from independent acceptance. Windows Sandbox command runtime failed during this phase; updating Codex CLI to 0.171.0 and running the sandbox unelevated restored it, after which real commands and evidence were rerun.

**Phase 3.** Fuel, Shade drain and dawn evaluation changed old victory and scoring assumptions. An ADR, migration ledger and requirement matrix helped identify which Phase 2 tests had to change and why. Browser E2E used valid inputs and read-only observation for the default campaign. A release-gate comparison found a Node/Chromium safe-boundary gameplay divergence and repaired it; two Night 3 mote coordinate representation differences remained documented. Phase 3 was tagged only after local checks and exact-SHA CI success. Official contract compatibility, real GPU, macOS and direct audio listening remained outside the verified scope.

**Phase 4.** The rendered benchmark uses a real Playwright Chromium scene with 200 active wandering Shades and 100 motes, rather than extrapolating from Core throughput. The same process soak runs ten rotating Nights with seeded inputs. Its results are reproducible as gameplay outcomes, but the required RSS ratio is not met: the official 35.27→47.94 MiB run and four further clean process runs exceed 1.20×. Two remediation rounds measured per Night RSS, V8 heap and external memory. Allocation reductions lowered absolute memory, yet did not meet the ratio; a terrain experiment without benefit was reverted. We paused further optimization rather than changing sampling points, forcing GC or hiding the failure. WS3 independently added disk persistence, CLI export, remapping and visual cues; this progress does not clear the soak blocker.

AI helped translate tickets into tests, generate repeatable scripts, inspect edge cases and keep evidence organized. Its mistakes included passing tests that missed browser behavior, premature readiness language and a Round 1 untracked memory trace overwritten during Round 2 diagnostics. That exact original trace could not be restored; other official failure evidence remains. `AGENTS.md`, the `verify-game` skill and hooks guided scope, regression commands and honest contract claims. The independent QA suite, headless harness and real browser tests supplied stronger evidence than narrative status updates.

There is no reliable token or cost telemetry for the full four phase history. A numerical total would be fabricated. A future estimate should export per-session model, input/output tokens and price, sum them by phase, and mark missing sessions before reporting a range. We reduced avoidable context by reading focused files, preserving test outputs and reusing short evidence summaries. If starting again, we would secure the official contract schema, create independent boundary tests before major Core changes, isolate historical proof files from new diagnostics, and profile RSS from the first soak implementation. The next release gate must resolve P4-SOAK-03 and recheck the distributable on each claimed platform.
