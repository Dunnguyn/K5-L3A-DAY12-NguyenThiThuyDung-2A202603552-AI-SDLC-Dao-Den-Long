# Leaderboard persistence and export

The built game and `/api/leaderboard` share one loopback Node process (`npm run start`, `127.0.0.1:4173`). One JSON file stores the top ten entries and submitted terminal-result UUIDs. Its default location comes from the OS user data directory; `DAO_DATA_DIR` selects an isolated profile for tests. The server serializes concurrent writes and writes a temporary file before rename. CLI export also writes through a temporary file and refuses to overwrite the authoritative store. Missing storage reads as an empty board; corrupt storage returns an error and CLI exit code 1 rather than silently resetting the board.

Browser E2E used ordinary movement input until a real Night 1 `no_flames` loss, submitted `Tester_1`, then read the saved entry from the menu. The browser and `node scripts/headless.mjs --export-leaderboard out.json` returned the same five-field entry from the same isolated file. The temporary profile was removed after the run; the actual observed entry is retained in `browser-e2e.json`. Unit/integration tests also reopened the store from disk, tested top-ten trimming, stable ties, duplicate submission and malformed files. `npm run start` was separately checked to return HTTP 200 for `/` and `/api/leaderboard`.

The server validates and sums `won_scores` from the Core campaign object sent by the browser, excluding the lost Night. A local player who edits browser data can forge the submitted score. This local, offline leaderboard provides accidental-duplicate prevention and input validation, not strong anti-cheat.
