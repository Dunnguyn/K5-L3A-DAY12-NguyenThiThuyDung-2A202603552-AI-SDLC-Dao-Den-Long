# Soak RSS investigation

The original ten-Night run completed 10 outcomes with zero crashes but rose from 41.37 to 63.00 MiB RSS. The saved trace shows step growth after Night 1 (47.88), Night 2 (52.38) and the third Night 2 (62.39), then a near plateau. It is not monotonic per Night. No prior GameState is stored in results/trace; only scalar outcome, seed, tick count and PID are retained. No new timers/listeners were observed. Event history was 26–123 items per completed Night; external and arrayBuffers were flat at about 1.73 and 0.018 MiB.

The separate diagnostic process sampled RSS, heapUsed and heapTotal at first initialization and each Night finish/next initialization/final reset. Before remediation, heapTotal stepped 6.31 → 11.56 → 16.31 → 25.56 MiB while heapUsed later fell to about 5.36 MiB; RSS stayed high. This points to repeated allocations expanding V8's heap and retained RSS pages, not evidence of a growing live JS object graph. It does not prove absence of every possible leak. The GC probe was run only in a separate diagnostic process *after* its soak measurement: heapUsed 7.34 → 4.77 MiB, RSS 48.92 → 48.46 MiB. No acceptance run used forced GC.

Identified avoidable allocations: `getWorld()` deep-cloned the entire map on every player pad check and every spawn update; periodic Core snapshots were cloned every 60 ticks although soak never reads them; Wander selected lantern targets by allocating and sorting filtered arrays per Shade; safe-zone scanning created arrays even when no lamp was active. The fix uses canonical world descriptors for read-only hot paths, omits only the unused periodic snapshot cache in soak states (normal Core keeps it), and chooses the same target by distance/ID without temporary arrays. No tuning, input, tick order, outcome or renderer geometry changed.

Diagnostics after those changes show lower heapTotal (about 12.56 MiB at final reset) and RSS around 47.73 MiB, but the official clean run still rose 35.27 → 47.94 MiB against a 42.33 MiB limit. Three additional clean processes all failed the same RSS criterion (47.02/47.71/47.64 MiB end). The remaining increase occurs largely during initial runtime execution/JIT/allocator expansion; live heap and external memory measurements do not show a comparable retained growth. This is a measured limitation, not an accepted PASS. Further investigation would need an independently justified memory strategy that preserves Ticket-04's exact sampling points and command.
